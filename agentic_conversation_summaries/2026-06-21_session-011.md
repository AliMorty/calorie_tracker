# Session 011 - Ingredient Dedup & USDA Macro Matching Pipeline

## What was done this session

- **Deduplicated the 1,115-ingredient list down to 913.** Instead of using `claude -p`
  in a loop (tried, too slow — one giant call took 5+ min), the dedup decisions were made
  by reading the full list directly. Built `apply_dedup.py` with a hand-curated merge map
  (202 removals: plurals, spelling variants, synonyms, same-macro variants). Script validates
  every index, refuses broken chains, reconciles counts (913 + 202 = 1115), and writes a
  human-readable `dedup_review.txt`. **Original `ingredients_set.json` left untouched.**
  Output: `ingredients_set_deduped.json` (913 items, macros still null).

- **Designed and tested the macro-matching pipeline** (USDA SR Legacy + LLM picker):
  1. Source list: `ingredients_set_deduped.json` (913 items).
  2. Reference: local `data/usda/foods_per_gram.csv` — 7,794 generic foods, per-gram macros.
  3. Retrieve: a Python weighted-lexical scorer picks ~15 candidate USDA rows per item.
  4. Judge: `claude -p` (sonnet) gets item + 15 candidates, returns best index or -1 (none).
     Runs in parallel chunks (~17 items), tolerant JSON parsing.
  5. Record: chosen row's macros ×100 = per-100g into JSON; -1 leaves null.

- **Iterated on retrieval quality:**
  - First naive substring scorer: ~6/10 on a random sample.
  - Added LLM-picks-from-candidates (index-based to fix a display bug where the model
    echoed the `(cal/100g=...)` suffix): much better.
  - Top-100 common items test: **84% matched.** Failures were plurals (apple vs USDA
    "Apples, raw") and generic-with-variants (milk, ketchup).
  - Added **plural-stemming + fuzzy word matching** to retrieval. Curated 50-item test
    (fat-variants + prior plural failures + generic mix): **96% matched (48/50).**
    Fat percentages handled precisely (greek yogurt 0/2/5%, milk 1/2/skim/whole,
    cottage cheese 1/2/4%, ground beef 10/27%). The 2 "none" were correct refusals
    (ketchup not in SR Legacy; ground beef 17% — USDA only has 10/15/20/25% steps).

## High-level notes for the developer

- **`claude -p` in a tight loop is the wrong tool for bulk work.** One huge single call is
  slow (5+ min for 1,115 items) and a single bad chunk can crash the run. The working pattern
  is: Python does retrieval + all bookkeeping; the LLM only makes per-item judgment calls on a
  small shortlist; run in parallel chunks with tolerant parsing.
- **Decisions-not-rewrite is the safety principle.** The LLM never rewrites the list — it
  returns indices/decisions, and Python applies them and reconciles counts so nothing
  silently disappears. This is how dedup stayed safe (913 + 202 = 1115).
- **Two USDA datasets exist locally.** `data/usda/foods_per_gram.csv` (SR Legacy, generic
  per-100g foods — used for macros) vs `data/usda_branded/` (1.8M branded products, barcodes —
  for later barcode lookups). SR Legacy is the right source for generic ingredient macros.
- **Retrieval is the bottleneck, not the LLM.** When matches failed it was almost always
  because the right USDA row never made the candidate shortlist (plurals, short common words
  drowning the plain entry). Improving the scorer (whole-word, plural-stemming, prefix boosts)
  drove the jump from 84% to 96%.
- **USDA "none" rate is expected** for branded/processed/exotic items — SR Legacy is a
  generic whole-foods catalog. Skipping them for now is intentional.

## Current challenges and anticipated risks

- **Raw vs cooked / prep state** — per-100g differs a lot (lentils raw 352 vs cooked 116).
  Need a consistent rule (likely raw as the stored base, convert at serving time) and to
  verify the LLM picks consistently.
- **`claude -p` flakiness** — chunks occasionally return non-JSON; the tolerant parser
  salvages or skips, but a skipped chunk means those items silently get no match. The full
  run should track which items got skipped and retry them.
- **Loose-but-wrong matches** — strict prompting reduces this, but some approximations slip
  through (e.g. earlier salt beef→pastrami). The full run needs a human review pass.
- **Serving sizes still unsolved** — USDA serving data is inconsistent; will need a separate
  decision/normalization step.
