## What was done this session

### Scan → "Add this to my food list" checkbox (Issue #17) — DONE, deployed, #17 closed
When a barcode scan finds a product, the food-detail (amount) screen now shows a checkbox
**"Add this to my food list (so I can reuse it later)"**. Tick it, set the amount, tap **Add food** →
the product is logged *and* saved to the per-user `user_foods` Supabase table for reuse.

Files changed:
- `index.html` — added a hidden `#fd-save-row` checkbox (`#fd-save`) to `#food-detail-screen`,
  reusing the existing `.mf-checkbox` style. Starts hidden via the global `.hidden` class
  (`display:none !important`, so it overrides `.mf-checkbox`'s `display:flex`).
- `js/app.js`
  - `lookupBarcode`: the returned food is now flagged `saveable: true` **only** for scanned foods
    (search/recent/manual results are not flagged, so they don't show the checkbox — manual entry
    already has its own save checkbox).
  - `onFoodConfirmed`: gained a trailing `saveToMyFoods` param. When true, it builds a **per-gram**
    record (`per100g / 100`, unit = `food.units[0].label`, i.e. `g`), calls `Storage.saveUserFood`,
    and pushes `_adaptFlatFood(perGram)` into `foodDatabase` so it's searchable immediately this
    session. **Dedup guard:** skips the save if a food with the same `name` already exists in
    `foodDatabase` (the `user_foods` table has no unique constraint).
- `js/ui.js`
  - `showFoodDetail`: shows/resets the checkbox row only when `food.saveable && !existingEntry`
    (never in edit mode); unchecks it each open.
  - The **Add food** click now computes `saveToMyFoods` (row visible + checkbox checked) and passes
    it through as the 6th arg to `onConfirm`.
- `sw.js` — `CACHE_VERSION` bumped `v16 → v17`.

**No database work needed** — reuses the existing `user_foods` table (created session 017 for manual
foods); same columns, no schema/SQL change. Confirmed this to Ali.

## High-level notes for the developer

- **The `saveable` flag is the switch for the new checkbox.** Only `lookupBarcode` sets it. If you ever
  want search results or other sources to offer "save to my foods", set `food.saveable = true` there
  too — the detail screen already handles it generically.
- **Per-gram is still the universal storage convention.** The scan-save path divides `per100g` by 100,
  matching manual-add, `user_foods`, and the shared `foods` table. Don't store per-100g.
- **Dedup is name-based and session-scoped.** The guard only sees foods loaded into `foodDatabase` this
  session. If a saved food didn't load (e.g. offline), a duplicate row could still be created — same
  limitation the app already has. A DB-side unique constraint on `(user_id, name)` would be the real
  fix but isn't in place.
- **Deploy = push to `main`** (GitHub Pages). `sw.js` `CACHE_VERSION` bumped to `v17` this session.
- **`gh` is read-only** — issues close via `closes #N` in commits landing on `main`.
