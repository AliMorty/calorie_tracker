# Session 013 - Serial Macro Match, Final DB Build, Supabase Swap (per-gram)

## What was done this session

### 1. New project rule: test small before scaling (CLAUDE.md)
- Ali was (rightly) annoyed that session 012 ran the whole 913-item match with 8 parallel
  `claude -p` workers on the first try — it caused silent rate-limit failures AND burned the
  token budget.
- Added a new section **"Test on Small Samples Before Scaling"** to `CLAUDE.md`:
  prove any expensive/LLM/bulk job on a tiny sample (5-10 items) first; **no parallelism without
  Ali's explicit permission**; flag token-heavy jobs before launching. Committed (6f367ef).

### 2. Small-sample test of the matching pipeline (50 items, serial)
- Built `data/usda/test_first50.py` — runs the macro-matcher on the FIRST 50 items only,
  **serially** (no parallelism), 2 chunks of 25.
- Result: **41/50 matched, 0 chunk failures**. Matches looked correct (cooked/raw forms right,
  fat levels sensible). Confirmed the pipeline logic is sound — the 012 disaster was parallelism,
  not the matcher.

### 3. Full 913 run — SERIAL + CHECKPOINTED
- Built `data/usda/build_macros_serial.py` (the real workhorse this session). Key differences
  from `build_macros.py`:
  - Processes the ~37 chunks **one at a time** (no ThreadPoolExecutor).
  - After each chunk, verifies **every** item got an int pick; retries the chunk once if any are
    missing.
  - If a chunk still fails, it **STOPS**, saves progress to `picks_cache.json`, and prints exactly
    which items/chunk failed. Re-running **resumes** from the cache (skips finished chunks).
  - Checkpoints `picks_cache.json` after every successful chunk — so running out of tokens loses
    at most the one in-flight chunk.
- Ran it (background). **Result: 663 matched / 250 none, exit 0, ZERO retries** — every chunk
  returned a complete set first try. Much better than 012's 533/380; confirms the inflated "none"
  rate there was purely the parallel rate-limiting.
- Outputs: `ingredients_macros.json` (macros + `usda_source`), `unmatched.json` (the 250 names),
  `macros_review.txt`.

### 4. Reviewed the 250 unmatched — honest finding
- Many "none"s are genuine USDA gaps (ethnic pastes/sauces: gochujang, doubanjiang, harissa,
  curry pastes, kecap manis; specialty cheeses: akkawi, nabulsi, oaxaca, paneer; regional spices:
  za'atar, sumac, mahlab, amchur; branded snacks: oreo, special k, all-bran, k-cups).
- BUT a chunk of them are **scorer-recall misses**, not real gaps — the right USDA row never made
  it into the 12 candidates due to vocabulary mismatch. Examples: **milk**, and **every cooked
  pasta** (spaghetti, penne, macaroni, etc. — "spaghetti" doesn't contain the word "pasta").
- Ali's decisions: doesn't eat pasta, so ignore those. Drop all 250 unmatched for now (names
  preserved in `unmatched.json` to revisit later). Get to using the app ASAP.

### 5. Milk turned out to be a non-issue
- Investigated why plain "milk" was unmatched. Found the dataset **already had** matched fat-tier
  variants: `milk, 1%` (42), `milk, 2%` (50), `milk, whole (3.25%)` (61), `milk, skim (0%)` (34).
  Only the vague "milk" entry was unmatched — and it's dropped with the other unmatched items.
- First attempt to "patch milk" (`build_final.py` adding 4 variants) created **duplicates** —
  caught it immediately and removed the patch. No milk changes were needed.

### 6. Final DB-ready file
- `data/usda/build_final.py`: keeps only matched records (`usda_source != null`) from
  `ingredients_macros.json`, drops unmatched, sorts by name.
- Output: `data/hand_crafted/ingredients_final.json` — **663 records**, each
  `{name, calories, protein, carbs, fat, usda_source}`.

### 7. Supabase swap (with a units bug fix)
- Inspected the app: `js/supabase.js` queries a `foods` table (`name, calories, protein, carbs,
  fat`) via `ilike` on name. `food_logs` **denormalizes** its own macro copies, so wiping `foods`
  does NOT harm logged history (only a loose optional `food_id`).
- This sandbox has **no network** to Supabase (curl fails, DNS unresolved), so the load is done by
  Ali pasting a generated SQL file into the **Supabase Dashboard → SQL Editor**.
- Generated `data/supabase_load.sql`: `ALTER TABLE ... ADD COLUMN IF NOT EXISTS usda_source text;`
  + `TRUNCATE TABLE foods;` + one big `INSERT` of all 663.
- **First load used per-100g values → beef showed 24,000 cal.** Root cause: `js/app.js:56,65`
  assumes the DB stores **per-GRAM** values and multiplies by 100. Our data was per-100g, so
  240 × 100 = 24,000.
- **Fix (Ali chose per-gram as the natural base unit):** regenerated `supabase_load.sql` using the
  ORIGINAL per-gram values from `usda/foods_per_gram.csv` (looked up via `usda_source`, full
  precision, round 5dp). Beef is now stored as `2.4` cal/g → app ×100 = correct 240/100g.
- Ali ran the corrected SQL. `SELECT count(*)` = 663 confirmed. App now shows correct calories.

## High-level notes for the developer
- **The DB stores PER-GRAM values now.** `js/app.js:56,65` multiplies by 100 to show per-100g.
  If you ever reload `foods`, keep values per-gram or the ×100 will blow up again. `supabase_load.sql`
  already does this correctly (sourced from `foods_per_gram.csv`).
- **`food_logs` is self-contained** — it copies name+macros at log time, so replacing the `foods`
  table never breaks meal history. `food_id` is just a loose optional pointer.
- **Serial + checkpoint is the pattern that worked.** `build_macros_serial.py` is the template for
  any future bulk `claude -p` job: one chunk at a time, verify every item, checkpoint, resume.
- **Never re-run with parallelism** without asking Ali (now a CLAUDE.md rule).
- **`unmatched.json` is the record of the 250 dropped items** — don't lose it; it's the to-revisit
  list.
- **This environment has no network to Supabase** — all DB writes go through Ali pasting SQL in the
  dashboard. Don't attempt direct pushes from here.
