# Session 007 - Swipe-to-Delete & Panel Animations

## What was done this session

- **Implemented swipe-to-delete** for food entries in the diary view
  - Swipe left on any food item to reveal a red "Delete" background
  - Swiping past 80px threshold triggers deletion with animation (slide out + collapse)
  - Swiping less than threshold snaps back to original position
  - Direction locking: first 8px of movement determines horizontal vs vertical intent, so scrolling isn't affected
  - Fixed browser back/forward navigation conflict with `touch-action: pan-y`
- **Added slide animations to all panels**
  - Add Food panel slides up from bottom on open, slides down on dismiss
  - Food Detail screen slides in from right on open, slides down on confirm, slides back right on X (cancel)
  - Overlay fades in/out instead of instant toggle
  - Fixed global `.hidden { display: none !important }` overriding transitions by adding specific overrides for animated panels
  - Fixed "spring" artifact on Food Detail exit by disabling transition before swapping CSS classes
- **Fixed panel layering** — Add Food panel now stays visible behind Food Detail when picking a food. Previously both panels animated simultaneously causing a janky visual.
  - X on Food Detail → slides right, reveals food list again
  - "Add food" confirm → Food Detail slides down, food list also dismisses
- **Made Add Food panel full screen** — changed from 72% height (top: 28%) to full height (top: 0), removed rounded top corners
- **Removed auto-focus on search input** — keyboard no longer appears immediately when Add Food panel opens; user taps the search box when ready
- **Added UX Polish Roadmap** to `design/UI_SPEC.md` — documented 6 prioritized improvements
- **Attempted and reverted automatic cache-busting** — dynamic timestamp approach worked but user preferred not to use it

## High-level notes for the developer

- **Animation pattern:** Panels use CSS `transform` + `transition` instead of `display: none` toggling. The `.hidden` class still exists globally but animated elements override it with `display: flex/block !important` so transforms can run.
- **Food Detail has asymmetric animation:** enters from right (`translateX(100%)` → `translateX(0)`), exits downward on confirm (`.hiding-down` class → `translateY(100%)`), exits right on cancel (back to `.hidden` → `translateX(100%)`).
- **Panel stacking:** Add Food panel (z-index 101) stays open behind Food Detail (z-index 200). On confirm, both dismiss. On cancel (X), only Food Detail dismisses.
- **No confirmation dialog on delete** — swipe-to-delete is instant (Telegram-style).
- **Pure CSS + JS implementation** — no external libraries for animations or gestures.
- **iPhone Safari caching remains unsolved** — users on home screen shortcuts must delete and re-add the shortcut to get updates.

## Current challenges and anticipated risks

- **iPhone caching** — the biggest UX pain point. No good solution for PWA home screen shortcuts on iOS without a service worker cache strategy.
- **No undo mechanism** — accidental swipe-deletes permanently remove the entry.
- **Desktop users can't delete** — no mouse-based delete option yet (only touch/simulated-touch works).
- **Animation class complexity** — the mix of `.hidden`, `.hiding-down`, `!important` overrides, and transition toggling is getting intricate. If more animated panels are added, consider a unified animation utility.
- **Re-render after delete** — full day re-renders after animation. Slow network could cause brief visual glitch.

## Planning Notes for Next Session (Barcode Scanner + Food Database)

### Library choice for barcode scanning
Use `html5-qrcode` or `quagga2` — both are JS libraries that access the phone camera and decode UPC/EAN barcodes in real-time. No native app needed, works in Safari and Chrome.

### Food database API
OpenFoodFacts (free, no API key required) supports both use cases:
- **Barcode lookup:** `https://world.openfoodfacts.org/api/v2/product/{barcode}`
- **Text search:** `https://world.openfoodfacts.org/cgi/search.pl?search_terms=oatmeal&json=1`

Good coverage for North American products, especially grocery items in Canada.

### User flow
1. User taps a camera/barcode icon in the Add Food panel
2. Camera opens, scans the barcode (UPC/EAN)
3. App hits OpenFoodFacts API with the barcode
4. Auto-fills food name, calories, protein, carbs, fat
5. User confirms quantity and logs it

### Why this works well together
Both barcode scanning and text-based food search use the same backend (OpenFoodFacts), so implementing one makes the other almost free. The text search replaces the current static JSON food list.
